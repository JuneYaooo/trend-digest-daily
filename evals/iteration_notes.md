# 迭代记录：从失败到修复

## 迭代 1（v0.1.0 开发期，用真实接口首跑）：百度热度字段误读、知乎标签是英文代码

- 过程：先用 `--limit 5` 温和试跑四个默认源，检查产物发现两处字段缺陷——
  ①百度条目 `hot_value` 出现 1、2、3 这样的数字：适配器把 `index`（卡内序号）当成了热度值；
  抓取原始响应核对后确认 wise 端点**根本不返回热度数值**，标签在 `newHotName`（如「热」），
  `hotTag` 是不公开映射的数字编码（实测 "3"↔「热」）。
  ②知乎 `hot_label` 输出英文 `hot`：`card_label` 里没有 text 字段，只有 `type` 代码。
- 归因：按调研文档的字段名假设实现，未先验证真实响应结构。
- 修复：百度改为 `hot_value=None`（hot_value_note 写明"该端点不返回热度数值，仅源内排名可比"），
  标签取 `newHotName`，`hotTag` 仅在非数字时原样保留、绝不猜编码；知乎增加
  `{hot→热, new→新, recommend→荐, discuss→讨论}` 映射，未知值原样保留。
- 另修复：normalize_url 折叠知乎问题链接时保留了 `api.zhihu.com` 与 `www.zhihu.com` 的差异，
  同一问题会生成两个缓存 key——现统一归并为 `www.zhihu.com/question/{id}`。

## 迭代 2（单元测试抓到）：已见缓存对标题变体条目重复膨胀

- 过程：`test_new_and_streak_marking` 断言缓存行数时失败（实际 6 行而非预期）——
  标题变体条目（如「台风…登陆」→「台风…沿海」）命中旧条目后，新条目按新 URL key 另起一行，
  与旧行并存；长期运行同一话题会在 seen.jsonl 里堆积多行。
- 归因：`build_seen_out` 只按条目自身 key 写入，未继承命中条目的旧 key。
- 修复：`apply_seen` 命中时记录 `matched_seen_key`，写缓存时原地更新旧条目
  （first_seen 保留、streak 累加、title 更新为最新措辞）；新增断言"行数=key 去重数"防回归。
- 结果：22/22 单测通过，缓存行数从 7→6（不重复）。

## 迭代 3（评测自检抓到）：评测脚本自身路径错误

- 过程：`run_cases.py` 首次运行即 FileNotFoundError——`parents[3]` 算错了仓库根目录。
- 修复：改为 `parents[2]`；一次性错误，未进入正式评测证据。

## 迭代 4（2026-09-19 第二次联网回归抓到）：GitHub Trending 页面改版混入赞助链接

- 过程：建仓数小时后复审，`--sources reddit,github_trending` 实测：Reddit 仍超时（如实标
  "源不可用"）；GitHub Trending 当日下午直连**可达**（与建仓时凌晨超时结论相反，直连可用性
  随网络环境波动），返回 18 条——但第 1 条是 `https://github.com/sponsors/explore`（非仓库、
  无 star 数）。再次取原始 HTML（当日对该源第 2 次也是最后一次请求，仅存 /tmp 分析）核对：
  页面已改为每个仓库一个 `<article>` 块，条目内新增 `/sponsors/{owner}` 赞助按钮（HTML 中可能
  出现在仓库标题链接之前），页面另有 `/sponsors/explore` 链接；旧适配器按 `<h2>` 切分取块内
  首个"仓库形"链接，于是把赞助链接当成条目（18 条中 1 条为假，真实仓库 17 个）。
- 归因：正则只按"两段路径"形状匹配，未排除 GitHub 保留路径前缀，也未锚定条目标题结构。
- 修复（v0.1.1）：改为 `<article>` 切分（无 `<article>` 时兼容旧 `<h2>` 布局）；仓库路径优先取
  `<h2>` 标题内的链接；新增保留路径前缀排除表（features/collections/trending/about/pricing/
  topics/sponsors）。对同份真实 HTML 离线重解析（不产生新请求）：17/17 仓库全量解析、零赞助
  条目；新增合成回归夹具 `trends_optional_v2/`（赞助按钮在标题链接之前的最坏布局）与单测，
  单测 22→24。四源（微博/知乎/百度/HN）同日两跑结构与字段完全一致，无漂移。

## 迭代 6（v0.2.0，2026-11-02）：对照外部调研的逻辑审查

起因：作者要求"每个项目都要去网上找对标、找参考逻辑，看当前逻辑是否有问题"。调研清单与出处见
[references/benchmarks.md](../references/benchmarks.md)。先用 v0.1.1 原样联网跑一遍（四源各 1 请求），
再把同一时刻的原始响应冻结下来，改前改后各跑一次做对比（[runs_v2/before_after_2026-11-02.json](runs_v2/before_after_2026-11-02.json)）。

### 改后结果（同一份原始响应）

- HN 名次与首页位置一致性：ρ −0.27 → 1.0；同源误并 1 → 0；百度#1 置顶 → 自然位（加油新规）。
- 断档 3 天后 streak：2 → 1（gap_days=3）；次日连续：两版都是 2（正常路径没变）。
- stdout：不可解析 → 合法 JSON。
- ASCII 关键词差异 6 处，全部是旧口径多出来的子串命中，其中 5 处明显误命中；
  paperclipai 那一条丢了 "AI"，但仍命中 "Agent"，领域判断不变。
- 同事件候选：当天 1 对（《后会友期》），2026-09-19 首跑数据 11 对，全部属于同一事件群（男篮输日本）。
- 当天跨源重合很少（只有 1 组跨源重复），RRF 前 10 里大多是各源 #1 并列——RRF 只在有跨源重合时有区分度，
  已写进 report-format（不能把并列当成同样热）。
- 测试 24 → 40；脚本层用例 7 → 13，全部通过。

### 新的已知限制

- HN 首页 HTML 解析依赖页面结构；改版即降级（可切 `--hn-mode algolia`，但名次含义随之改变）。
- `rank_delta`、连续在榜在真实多日数据上还没验证，本轮只用合成缓存和模拟日期验证。
- 关键词规则会漏掉全小写拼在别的词里的缩写（如 `paperclipai`），这是用召回换精度。

## 已知限制（v0.1.x 时记录，v0.2.0 仍适用的部分）

- 判定为开发 Agent 自评（model_only），未独立人工复核。
- 跨源聚类是"脚本标重复 + agent 保守合并"：标题措辞差异大的同一事件（尤其跨语言）不会被脚本
  自动合并，依赖 agent 判断，可能漏并；宁漏勿错（禁止误并）是既定取舍。
- 微博/知乎/百度均为无契约的公开端点（详见 references/sources.md），改版风险由每源独立降级兜底，
  但不保证当日可用；`s.weibo.com` 搜索链接需登录才能看完整内容，已如实标注。
- GitHub Trending 依赖 HTML 结构正则，页面改版即失效（列于可选源）。
- 热度数值仅源内可比；跨源排序是 AI 建议而非客观度量。
