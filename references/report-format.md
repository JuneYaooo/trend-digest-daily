# 日报格式规范（reports/YYYY-MM-DD.md）

agent 依本规范把 `fetch_trends.py` 的规范化 JSON 渲染成每日选题建议。所有热度、排名、
链接必须取自当日 JSON，禁止编造 JSON 中不存在的条目或数字；聚合顺序是 AI 建议而非官方排名。

v0.2.0 起，排序和领域命中所需的确定性信号都由脚本算好（`fusion` / `domain_hits` / `related` /
`rank_delta` / `gap_days`），agent 负责的是"判断与表达"：确认同事件、剔除语义上不相关的关键词命中、
写角度。这样同一份 JSON 交给不同 agent，选题顺序基本一致，差异只在文字上。

## 结构模板

```markdown
# 选题雷达 · {YYYY-MM-DD}（周X）

> 数据源：{成功源列表}｜共 {total_items} 条 → 去重后 {unique_items} 条
>（跨源重复 {duplicate_items}，跨源同发 {multi_source_topics}，NEW {new_items}）
> 源状态：{每源一行，不可用源写明「源不可用：原因」；有 skipped 的写「已跳过 N 条置顶/广告位」}

## 今日必看（3-5 张选题卡）

### 1. {话题名，一句人话} ｜匹配度★★★★☆｜{领域 label}
- **热度证据**：{源#排名（标签）}，如：微博#1（新）· 百度#21；HN 写「HN 首页#6 · 22 points」
- **发生了什么**：一句话，基于条目标题，不脑补细节
- **为什么和你有关**：一句话，写出命中的关键词（来自 domain_hits）与关联逻辑
- **可写角度**：①… ②… ③…（结合博主领域，具体到可动笔）
- **时效窗口**：如 24h 内（标签：爆）｜上升中（较上次 +N 名）｜3 天内｜长尾
- **链接**：{原帖标题}(URL)｜{…}(URL)

## 次级观察（值得蹲但还不够热/领域相关度低）
- {条目}｜{源#排名}｜一句为什么先蹲着

## 全源速览
| # | 标题 | 来源·排名 | 热度 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | … | 微博#1 | 398487 | NEW / 连续N天 / 回潮 / ↑N |

## 趋势追踪
- 连续在榜（streak ≥2）：{标题}：连续 {streak} 天，首见 {first_seen}，今日 {源}#{rank}（较昨日 {rank_delta:+}）
- 回潮（gap_days 非空）：{标题}：断档 {gap_days} 天后再次上榜，首见 {first_seen}
- （首次运行无历史缓存时写：首日基线，明日开始出现连续在榜追踪）

---
*聚合顺序与切入角度为 AI 建议仅供参考；排名为各平台自己的榜单位置（rank_basis），热度口径互不可比；
发布前请点开原帖核实内容。生成：trend-digest-daily v0.2.0*
```

## 聚类、排序与打分规则

1. **跨源聚类**：
   - `dup_of` 非空的条目一律并入主条目（脚本只在**不同源**之间判重，同一榜单内不会互相合并）。
   - `related` 是"包含度 ≥0.6"的同事件**候选**（如「郭士强 下课」⊂「…网友称让郭士强下课，如何评价」），
     agent 读标题确认是同一事件才合并，并在热度证据里列出全部佐证；拿不准就拆开。
   - 英文条目不计算 `related`，跨语言同事件只能靠 agent 判断（保守，宁漏勿错）。
2. **领域匹配度**（只用 `domain_hits`，不自己再做字符串匹配）：
   - 某话题全部条目的 `domain_hits[].matched` 去重后：1 个关键词 ★★，2-3 个 ★★★，
     4 个以上或直接命中账号定位 ★★★★-★★★★★。
   - 命中但语义无关（如「工作」出现在与职场无关的问句里）：可以降级到「次级观察」，并写明原因；
     不允许把没有任何命中的话题升为 ★★★ 以上——若确实语义相关（如标题写 language model 但没有
     关键词），最多 ★★ 并标注「语义相关，无关键词命中」。
   - 没有 `domain_hits` 字段（未传 `--config` 或配置无法解析，见 `notes.domain_matching`）→ 输出通用版。
3. **今日必看的排序**：先按匹配度星级，同星级按 `fusion.rrf_score` 降序（跨源同发 > 单源高位），
   再按标签（爆 > 热 > 新）。通用版直接按 `fusion.rrf_score` 取 Top 3-5。
   RRF 只用名次（Σ 1/(60+rank)），所以「跨源同发」天然排前；当天跨源重合少时（如 2026-11-02 仅 1 组），
   各源 #1 分数相同，必须靠领域匹配与标签区分，不要把 RRF 的并列当成"同样热"。
4. **热度证据的写法**：引用 `源#rank` + `hot_label`；HN 的 rank 是首页真实位置（见 `rank_basis`），
   points 只作补充。百度无热度数值，只写名次。不同源的 `hot_value` 绝不相加、换算或比较。
5. **时效窗口**：
   - `hot_label` 为「爆/热」或微博 `extra.onboard_time` 显示刚上榜（数小时内）→ 24h 内；
   - `rank_delta` > 0（较上次运行名次上升）→ 写「上升中（↑N）」，优先跟；
   - `streak` ≥ 2 → 可做深度解读；`gap_days` 非空 → 「回潮」，适合做复盘/后续；
   - 英文源 → 注明适合编译/解读类账号。
6. **诚实红线**：某源不可用必须在「源状态」注明；NEW/streak/rank_delta/gap_days 只能来自 JSON 字段，
   不得推算；热度数字原样引用；跳过的置顶/广告位不写进榜单。
